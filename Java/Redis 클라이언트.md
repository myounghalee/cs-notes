## Redis 클라이언트란?

Redis 서버는 그 자체로는 그냥 명령어를 받아 처리하는 프로그램이에요. Java 애플리케이션에서 Redis에 `SET`, `GET` 같은 명령을 보내려면, 그 통신을 대신 처리해주는 **클라이언트 라이브러리**가 필요해요. Java 진영에서 대표적인 세 가지가 **Jedis, Lettuce, Redisson**이에요.

> **비유**: Redis 서버가 "전화를 받는 상담원"이라면, 클라이언트 라이브러리는 그 상담원에게 전화를 거는 **전화기**예요. Jedis는 한 통씩 순서대로 거는 옛날 전화기, Lettuce는 여러 통화를 동시에 처리할 수 있는 최신 통화 시스템, Redisson은 "전화 걸기"를 넘어 아예 "비서"처럼 락 관리, 분산 자료구조 같은 고급 업무까지 대신 처리해주는 느낌이에요.

## Jedis — 가장 오래된, 단순한 동기 클라이언트

**Jedis**는 Java Redis 클라이언트 중 가장 오래되고 단순한 라이브러리예요. **동기(Blocking) 방식**으로 동작해요 — 명령을 보내면 응답이 올 때까지 그 스레드가 멈춰서 기다려요.

```java
try (Jedis jedis = jedisPool.getResource()) { // 커넥션 풀에서 하나를 빌려옴
    jedis.set("key", "value");
    String value = jedis.get("key"); // 응답 올 때까지 스레드가 대기(블로킹)
}
```

**Jedis 인스턴스 하나는 스레드 안전하지 않아요.** 그래서 여러 스레드가 동시에 Redis를 쓰려면, **스레드 개수만큼 커넥션을 미리 만들어두는 커넥션 풀(Connection Pool)** 이 필수예요. 스레드가 많아질수록 그만큼 커넥션도 많이 필요해서, 자원을 꽤 소모해요.

## Lettuce — 비동기/논블로킹, Spring Boot의 기본 선택

**Lettuce**는 Netty(비동기 네트워킹 프레임워크) 기반으로 만들어진 클라이언트예요. **비동기(Async)/논블로킹(Non-blocking)** 방식을 지원하고, **커넥션 하나로 여러 스레드가 동시에 안전하게 사용**할 수 있어요.

```java
RedisAsyncCommands<String, String> commands = connection.async();
RedisFuture<String> future = commands.get("key"); // 스레드를 안 막고 바로 반환됨
future.thenAccept(value -> System.out.println(value)); // 응답이 오면 나중에 처리
```

**커넥션 하나가 스레드 안전**하기 때문에, Jedis처럼 스레드마다 커넥션을 따로 두지 않아도 돼요. 이 덕분에 **적은 수의 커넥션으로도 훨씬 많은 요청을 처리**할 수 있어요. 이런 효율성 때문에 **Spring Boot는 Redis 연동 시 기본 클라이언트로 Lettuce를 채택**하고 있어요.

## Redisson — 캐시를 넘어 분산 기능까지

**Redisson**은 단순히 Redis에 명령을 보내는 걸 넘어서, Redis를 이용한 **고수준 분산 기능**을 자바 객체처럼 편하게 쓸 수 있게 해줘요. [[../Database/동시성 이슈와 락|동시성 이슈와 락]]에서 다룬 **분산 락**이 대표적인 예시예요.

```java
RLock lock = redissonClient.getLock("product:lock:" + productId);
try {
    lock.lock(); // 여러 서버에 걸친 락을 자바 코드처럼 간단하게 사용
    // ... 임계 영역 로직
} finally {
    lock.unlock();
}
```

이 외에도 분산 환경에서 쓸 수 있는 `RMap`(분산 Map), `RQueue`(분산 큐), `RAtomicLong`(분산 카운터) 같은 **자바의 표준 자료구조와 비슷한 인터페이스를 분산 버전으로 제공**해요. 개발자는 "이게 Redis로 구현됐다"는 걸 거의 신경 쓰지 않고, 마치 로컬 자바 객체를 쓰듯 코드를 짤 수 있어요.

## 세 클라이언트 비교

| 구분              | Jedis             | Lettuce             | Redisson               |
| --------------- | ----------------- | ------------------- | ---------------------- |
| 통신 방식           | 동기(Blocking)      | 비동기/논블로킹 (Netty 기반) | 비동기/논블로킹 (Netty 기반)    |
| 스레드 안전성         | ❌ (스레드마다 커넥션 필요)  | ✅ (커넥션 하나 공유 가능)    | ✅                      |
| 제공 수준           | Redis 명령어를 그대로 래핑 | Redis 명령어를 그대로 래핑   | 분산 락, 분산 자료구조 등 고수준 기능 |
| Spring Boot 기본값 | ❌ (예전 기본값이었음)     | ✅ (현재 기본 클라이언트)     | ❌ (필요시 별도 추가)          |
| 학습 난이도          | 낮음 (단순함)          | 낮음~중간               | 중간 (기능이 많음)            |

## 언제 무엇을 써야 할까?

- **단순 캐시 용도(GET/SET 위주)**: Spring Boot 기본값인 **Lettuce**로 충분해요. 대부분의 경우 이걸 그대로 쓰면 돼요.
- **분산 락, 분산 자료구조가 필요할 때**: **Redisson**을 추가로 도입해요. [[../Database/동시성 이슈와 락|동시성 이슈와 락]]에서처럼 여러 서버에 걸친 동시성 제어가 필요하면 Redisson이 훨씬 편해요.
- **Jedis**: 레거시 프로젝트가 아니라면 요즘 새로 시작하는 프로젝트에서 굳이 선택할 이유는 적어요. 다만 여전히 단순하고 널리 쓰여온 만큼 예제/자료가 많다는 장점은 있어요.

> Lettuce와 Redisson은 경쟁 관계가 아니라 **함께 쓰이는 경우도 흔해요** — 일반적인 캐시 조회는 Lettuce(Spring Data Redis)로, 분산 락처럼 특별한 기능이 필요한 부분만 Redisson을 추가로 쓰는 식이에요.

## Q&A로 복습하기

### Q. Jedis가 스레드마다 별도 커넥션을 필요로 하는 이유는?
A. Jedis 인스턴스 하나는 스레드 안전하지 않기 때문에, 여러 스레드가 동시에 Redis를 사용하려면 커넥션 풀에서 스레드 개수만큼 커넥션을 확보해야 한다.

### Q. Lettuce가 Spring Boot의 기본 Redis 클라이언트로 채택된 이유는?
A. Netty 기반의 비동기/논블로킹 방식으로 동작하며 커넥션 하나를 여러 스레드가 안전하게 공유할 수 있어, Jedis보다 적은 자원으로 더 많은 요청을 효율적으로 처리할 수 있기 때문이다.

### Q. Redisson이 Jedis/Lettuce와 근본적으로 다른 점은?
A. Jedis와 Lettuce는 Redis 명령어를 그대로 래핑해서 제공하는 반면, Redisson은 분산 락이나 분산 자료구조처럼 Redis를 활용한 고수준 기능을 자바 객체처럼 편하게 쓸 수 있도록 추상화해서 제공한다.

### Q. 단순 캐시 용도와 분산 락이 모두 필요한 프로젝트라면 어떻게 클라이언트를 선택하는 것이 좋은가?
A. 일반적인 캐시 조회는 Spring Boot 기본값인 Lettuce로 처리하고, 분산 락처럼 Lettuce만으로는 구현이 번거로운 기능만 Redisson을 추가로 도입해 함께 사용하는 것이 실무에서 흔한 방식이다.
