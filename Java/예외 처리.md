## Error는 왜 잡으면 안 될까?

[[Java]]에서 본 것처럼 `Throwable`은 `Error`와 `Exception`으로 나뉘어요. 이 둘의 차이는 단순한 분류가 아니라 **"잡아서 복구를 시도해도 되는가"** 에 대한 근본적인 구분이에요.

```java
try {
    riskyOperation();
} catch (OutOfMemoryError e) { // ⚠️ 이렇게 잡는다고 해결되지 않음
    System.out.println("메모리 부족하지만 계속 진행할게요!"); // 대부분 여기서 또 터짐
}
```

`OutOfMemoryError`, `StackOverflowError` 같은 **`Error`는 JVM 자체의 심각한 문제**예요. 힙이 꽉 찼거나 스택이 넘쳤다는 건, 애플리케이션 코드로 "잡아서 처리"할 수 있는 수준을 이미 넘어선 상황이에요. **`Error`를 catch하는 건 실무에서 거의 안티패턴으로 취급**돼요 — 잡아봤자 문제가 해결되지 않고, 오히려 진짜 심각한 문제를 숨기는 부작용만 생겨요.

반면 `Exception`은 **애플리케이션 로직에서 발생하는, 코드로 대응할 수 있는 문제**예요. 그래서 우리가 평소에 `try-catch`로 다루는 건 대부분 `Exception`(과 그 하위)이에요.

## 자바에 있는 주요 예외 종류

자바 표준 라이브러리에는 자주 발생하는 상황에 맞춰 이미 만들어둔 예외 클래스들이 많아요. 실무/면접에서 자주 마주치는 것들을 정리해볼게요.

### 자주 만나는 Unchecked Exception (RuntimeException 계열)

| 예외 | 발생 상황 |
|---|---|
| `NullPointerException` | `null`인 참조 변수의 메서드/필드에 접근할 때 |
| `ArrayIndexOutOfBoundsException` | 배열의 실제 범위를 벗어난 인덱스에 접근할 때 |
| `IndexOutOfBoundsException` | `List` 등 컬렉션에서 범위를 벗어난 인덱스에 접근할 때 (위 예외의 좀 더 넓은 상위 버전) |
| `ClassCastException` | 호환되지 않는 타입으로 강제 형변환할 때 |
| `NumberFormatException` | `"abc"`처럼 숫자로 바꿀 수 없는 문자열을 `Integer.parseInt()` 등으로 변환할 때 |
| `ArithmeticException` | 정수를 0으로 나누는 등 산술 연산 자체가 불가능할 때 |
| `IllegalArgumentException` | 메서드에 부적절한(허용 범위를 벗어난) 인자를 전달했을 때 |
| `IllegalStateException` | 객체가 그 메서드를 호출하기에 적절하지 않은 상태일 때 |
| `UnsupportedOperationException` | 지원하지 않는 연산을 호출했을 때 (예: [[컬렉션]]에서 다룬 불변 리스트에 `add()` 시도) |
| `ConcurrentModificationException` | [[컬렉션]]에서 다룬 fail-fast — 순회 중인 컬렉션을 직접 수정했을 때 |

```java
Integer.parseInt("abc");         // NumberFormatException
int[] arr = new int[3];
arr[5] = 1;                       // ArrayIndexOutOfBoundsException
Object o = "문자열";
Integer i = (Integer) o;          // ClassCastException
```

### 자주 만나는 Checked Exception

| 예외 | 발생 상황 |
|---|---|
| `IOException` | 파일/네트워크 등 입출력 작업이 실패했을 때 |
| `FileNotFoundException` | (`IOException`의 하위) 열려는 파일이 존재하지 않을 때 |
| `SQLException` | DB 작업(쿼리 실행 등)이 실패했을 때 |
| `ClassNotFoundException` | `Class.forName()` 등으로 찾으려는 클래스가 클래스패스에 없을 때 |
| `InterruptedException` | [[동시성]]에서 다룬 것처럼, `sleep()`/`wait()` 등으로 대기 중인 스레드가 인터럽트당했을 때 |

> **구분 팁**: 대부분 **"프로그래머가 코드를 실수로 잘못 짜서" 나는 건 Unchecked**(NPE, 배열 범위 초과, 잘못된 형변환 등)이고, **"내 코드는 맞는데 외부 환경(파일, 네트워크, DB) 문제로" 나는 건 Checked**인 경우가 많아요.

이 분류에서 헷갈리기 쉬운 것 하나 — `NumberFormatException`은 이름만 보면 "형식이 안 맞는 외부 데이터 문제"처럼 보이지만, 사실 `IllegalArgumentException`의 하위 클래스라 **Unchecked**예요. 자바 표준 라이브러리에서도 **"입력값 검증 실패"는 대체로 Unchecked로 처리**한다는 흐름을 보여주는 사례예요.

## Checked Exception, 정말 좋기만 할까? — 실무의 논쟁

[[Java]]에서 Checked Exception을 "컴파일러가 처리를 강제해서 안전하다"고 소개했는데, 사실 실무에서는 **찬반이 갈리는 주제**예요.

```java
void processOrder() throws SQLException, IOException, TimeoutException {
    // 메서드 시그니처가 예외 목록으로 뒤덮임
}
```

**Checked Exception의 문제점**:
- 메서드가 예외를 처리 안 하고 그냥 위로 던지려면(`throws`), **호출하는 모든 메서드의 시그니처에 이 예외가 전파**돼요. 계층이 깊어질수록 모든 메서드에 `throws` 목록이 줄줄이 붙어요.
- 람다식 안에서는 Checked Exception을 던지는 코드를 넣기가 까다로워요(함수형 인터페이스가 checked exception을 허용 안 함).

그래서 **Spring 같은 현대 프레임워크는 Unchecked Exception(RuntimeException 계열)을 기본 전략으로 채택**해요. 예를 들어 Spring의 `DataAccessException`은 DB 관련 여러 Checked Exception(`SQLException` 등)을 감싸서 **Unchecked로 다시 던져줘요.**

```java
// Spring Data JPA — 내부적으로 SQLException을 잡아서 Unchecked로 변환해 던짐
Order order = orderRepository.findById(id) // SQLException을 직접 처리할 필요 없음
    .orElseThrow(() -> new OrderNotFoundException(id));
```

> **정리**: "호출자가 반드시 대비해야 하는, 복구 가능한 외부 요인"이라면 Checked도 여전히 의미 있지만, 대부분의 경우 **"예외가 발생하면 요청 전체를 실패 처리하고 로그를 남기는 것"** 이 흔한 대응이라, 굳이 모든 메서드에 `throws`를 전파시키기보다 Unchecked로 통일하는 게 실무에서 더 선호돼요.

## 커스텀 예외 만들기

애플리케이션 고유의 예외 상황은 직접 예외 클래스를 만들어서 표현해요.

```java
class OrderNotFoundException extends RuntimeException { // Unchecked로 만드는 게 요즘 흔한 선택
    public OrderNotFoundException(Long orderId) {
        super("주문을 찾을 수 없습니다. id=" + orderId);
    }
}
```

```java
Order order = orderRepository.findById(id)
    .orElseThrow(() -> new OrderNotFoundException(id));
```

`RuntimeException`(Unchecked)을 상속할지 `Exception`(Checked)을 상속할지는, **"호출자가 이 예외를 보고 즉시 대응 코드를 짜야만 하는가"** 를 기준으로 판단해요. 앞서 본 것처럼 실무에서는 **Unchecked로 만드는 게 일반적인 흐름**이에요.

## 예외 체이닝 — 원인을 잃어버리지 않기

낮은 레벨의 예외를 더 의미 있는 예외로 바꿔서 던질 때, **원래 원인을 놓치면 디버깅이 매우 어려워져요.**

```java
// 나쁜 예 — 원인이 사라짐
try {
    parseFile(file);
} catch (IOException e) {
    throw new FileProcessException("파일 처리 실패"); // 원래 IOException 정보가 사라짐!
}
```

```java
// 좋은 예 — 원인을 담아서 재던지기 (Exception Chaining)
try {
    parseFile(file);
} catch (IOException e) {
    throw new FileProcessException("파일 처리 실패", e); // e를 cause로 함께 전달
}
```

```java
class FileProcessException extends RuntimeException {
    public FileProcessException(String message, Throwable cause) {
        super(message, cause); // Throwable의 (message, cause) 생성자 활용
    }
}
```

이렇게 하면 나중에 스택 트레이스를 볼 때 **"진짜 원인이 무엇이었는지"(Caused by: ...)** 까지 함께 확인할 수 있어요.

## Multi-catch — 여러 예외를 한 번에

여러 예외를 **같은 방식으로 처리**하고 싶을 때, Java 7부터는 `|`로 묶어서 한 번에 잡을 수 있어요.

```java
try {
    riskyOperation();
} catch (IOException | SQLException e) { // 두 예외를 동일하게 처리
    log.error("작업 실패", e);
    throw new ServiceException(e);
}
```

각 예외 타입마다 `catch` 블록을 따로 만들어서 **똑같은 코드를 중복**시키던 문제를 줄여줘요.

---

## 예외 처리 안티패턴

- **빈 catch 블록**: 가장 나쁜 습관이에요. 예외가 발생했다는 사실 자체를 조용히 삼켜버려서, 나중에 문제가 터져도 원인을 추적할 단서가 사라져요.
  ```java
  try {
      riskyOperation();
  } catch (Exception e) {} // ❌ 최악 — 무슨 일이 있었는지 아무 기록도 안 남음
  ```
- **너무 광범위한 catch**: `catch (Exception e)`처럼 최상위로 잡으면, **예상 못 한 다른 종류의 버그까지 다 삼켜버려서** 진짜 문제를 놓칠 수 있어요. 가능한 한 구체적인 예외 타입을 잡는 게 안전해요.
- **예외를 흐름 제어에 사용**: 정상적인 로직 분기를 `if`가 아니라 예외로 처리하면, 코드 흐름을 읽기 어렵고 성능도 떨어져요(예외 생성 자체가 스택 트레이스를 채우는 비용이 있음).

## 한 장 요약

| 질문 | 답 |
|---|---|
| Error를 catch하면 안 되는 이유는? | JVM 레벨의 심각한 문제라 애플리케이션 코드로 복구 불가능 |
| 대표적인 Unchecked 예외는? | NPE, ArrayIndexOutOfBoundsException, ClassCastException, IllegalArgumentException 등 |
| 대표적인 Checked 예외는? | IOException, SQLException, ClassNotFoundException 등 |
| 왜 실무에서 Unchecked Exception을 선호하나? | Checked는 throws가 메서드 시그니처를 계속 오염시키고 람다와도 궁합이 안 좋음 |
| 커스텀 예외는 보통 무엇을 상속하나? | RuntimeException(Unchecked) — 특별히 강제 처리가 필요한 경우만 Checked |
| 예외 체이닝이 필요한 이유는? | 원래 예외(cause)를 유지해야 나중에 진짜 원인을 추적할 수 있음 |
| 빈 catch 블록이 위험한 이유는? | 문제가 조용히 묻혀서 나중에 원인 추적이 불가능해짐 |

## Q&A로 복습하기

### Q. OutOfMemoryError를 catch해서 처리하면 안 되는 이유는?
A. Error는 JVM 자체의 심각한 문제를 나타내는데, 이미 애플리케이션 코드가 대응할 수 있는 수준을 넘어선 상황이라 catch해도 실질적으로 복구되지 않고, 오히려 심각한 문제를 숨겨버릴 수 있기 때문이다.

### Q. NumberFormatException은 Checked인가 Unchecked인가?
A. Unchecked다. IllegalArgumentException의 하위 클래스로, 입력값 검증 실패는 외부 요인이라기보다 대체로 처리 가능한 프로그램 로직의 문제로 취급되어 Unchecked로 설계되어 있다.

### Q. Checked Exception과 Unchecked Exception을 구분하는 실질적인 기준은?
A. 프로그래머의 실수(잘못된 배열 인덱스, null 접근, 잘못된 형변환 등)로 발생하는 것은 대체로 Unchecked이고, 파일/네트워크/DB처럼 내 코드는 맞아도 외부 환경 문제로 발생하는 것은 대체로 Checked인 경우가 많다.

### Q. Checked Exception이 실무에서 비판받는 이유는?
A. 예외를 처리하지 않고 위로 던지려면 호출 체인의 모든 메서드 시그니처에 throws가 전파되어야 하고, 함수형 인터페이스(람다)와도 잘 맞지 않아 코드가 번잡해지기 때문이다.

### Q. 예외 체이닝을 하지 않고 새 예외만 던지면 어떤 문제가 생기나?
A. 원래 발생한 예외(원인)에 대한 정보가 사라져서, 스택 트레이스만으로는 실제 문제의 근본 원인을 추적하기 어려워진다.

### Q. 빈 catch 블록이 안티패턴인 이유는?
A. 예외가 발생했다는 사실을 아무 기록 없이 조용히 무시해버려서, 나중에 관련 문제가 터졌을 때 원인을 추적할 단서가 전혀 남지 않기 때문이다.

### Q. 커스텀 예외를 만들 때 Unchecked로 만드는 것이 흔한 이유는?
A. 대부분의 예외 상황은 요청 전체를 실패 처리하고 로그를 남기는 식으로 대응하는 경우가 많아, 모든 호출 계층에 throws를 강제로 전파시키는 Checked Exception보다 Unchecked Exception이 실무에서 더 편리하기 때문이다.
